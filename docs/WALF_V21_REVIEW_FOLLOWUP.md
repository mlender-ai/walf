# WALF V2.1 · 최종 코드 리뷰 후속 보고

대상: `mlender-ai/walf` PR #2 · 기준 커밋 `cb0f5f3` · 브랜치 `feat/walf-v2.1`
범위: 리뷰에서 지적한 최우선 수정 5개 + 제품 검증. 병합하지 않았고, 자동 병합도 켜지 않았어요.

## 1. 최우선 수정 5개

### 1-1 품번 부분 문자열로 같은 상품을 확정하지 않는다 — `server/src/sameproduct.ts`
- **전**: 페이지 제목을 붙여 쓴 문자열에 찾는 품번이 **포함**되면 같은 상품(`same_code`)이었다. 품번을 먼저 보고 바로 돌려줘서 브랜드가 달라도 같은 상품이 될 수 있었다.
- **후**
  - 순서를 바꿨다. **브랜드 충돌**을 먼저 보고, 다르면 품번이 같아도 `different`로 판정한다.
  - 품번은 제목을 품번 단위 조각으로 나눈 뒤 **정확히 같을 때만** 근거가 된다(`codeOnPage`). 예외는 품번 뒤에 색·사이즈만 붙은 옵션 표기(`W-JKT26-055-NAVY`) 하나다.
  - **품번 충돌**: 페이지에 다른 품번만 있으면 `different`다. 같은 품번과 다른 품번이 함께 있으면 확정하지 않는다.
  - 짧은 품번(`M65`처럼 6자 미만)은 품번만으로 같은 상품이라고 하지 않는다(`strongCode`).
  - 시즌 표기(`FW2024`·`SS25`)는 품번으로 보지 않는다.
  - 브랜드도 부분 문자열로 맞추지 않는다(`ADER` ≠ `ADERERROR`). 한글·영문 표기는 별칭(brands 표·공식몰 목록)으로만 같은 브랜드로 본다.
  - 판매처 탐색과 기다려줘 페이지 동일성 모두 별칭을 넘긴다.
- 상품명 핵심 단어만 같으면 지금처럼 `likely`(가능성 높음)까지다.

### 1-2 `likely → matched` 자동 승격 제거 — `server/src/watch.ts`
- **전**: 상품명만 같아도 페이지 동일성이 `matched`가 됐다. 그러면 목표가·재고가 맞을 때 “기다리던 가격이 됐어요” 알림이 나갔다.
- **후**
  - `likely`는 그대로 `likely`로 둔다. 같은 상품으로 보지 않으므로(`PAGE_OK` 밖) 목표가·재고가 맞아도 상태는 `unverified`(확인할 게 있어요)이고 알림은 없다.
  - 어드민 기다려줘 대기열에 “같은 상품일 가능성 높음 · 확인 필요”로 올라간다. 운영자가 “같은 상품 페이지 맞음”을 누른 뒤에만 조건 충족 알림이 간다.
  - 서버를 시작할 때 예전 규칙으로 `matched`가 된 감시를 지금 규칙으로 다시 판정한다(`resettleAutoMatched`). 페이지를 다시 열지 않는다. 조건 충족이 풀리면 “조건이 다시 맞지 않아요”로 기록한다.

### 1-3 새 매물 알림은 조건을 모두 확인했을 때만, `possible`은 따로 — `server/src/offers.ts`(`fitOf`) · `offerreview.ts`
- **전**: 새 매물 알림 조건(`meetsWatch`)에 몇 가지가 빠져 있었다.
  - 색상을 보지 않았다.
  - 재고·상태를 모르면 통과시켰다.
  - 할인가를 확정 가격처럼 썼다.
  - `possible` 후보도 확정 상품과 같은 알림(“다른 판매처에서 원하는 조건의 매물을 찾았어요”)을 보냈다.
- **후**: `fitOf`가 원하는 색상·사이즈 재고·상품 상태·배송비 포함 목표가를 하나씩 본다.
  - 모두 **확인됨**일 때만 `met`이다.
  - 모르는 값(배송비·재고·색상·새 상품 여부·할인 적용 조건)이 하나라도 있으면 `unknown`이다. 충족이 아니므로 알림이 없다.
  - 가격은 판매가 기준이다. 할인가만 목표 이하이면 `unknown`이다(가격 감시의 `sale_only`와 같은 규칙).
  - `exact` + `met`이면 `watch_discovery` 알림을 보낸다. 문구는 “왈프 팀이 같은 상품인지 확인했어요”다.
  - `possible` + `met`이면 **`watch_discovery_possible`** 알림을 따로 보낸다. 제목은 “같은 옷일 수 있는 매물이 있어요”, 본문은 “아직 확정하지 못했어요 · 품번·사진을 꼭 확인해 주세요”다. 같은 페이지는 한 번만 보낸다.
  - 운영자 화면과 기다려줘 기록에 “확인하지 못한 조건: …” 또는 “조건과 달라요: …”를 남긴다.
  - 검수 기록(`review_log.auto.fit`)에도 남겨 평가 데이터로 쓴다.

### 1-4 기기 ID만으로 이전 계정을 가져가는 길 차단 — `server/src/domain.ts` · `api.ts` · `admin.ts` · 앱 `lib/api.ts` · `(tabs)/my.tsx`
- **전**: 토큰 발급 전(이전 버전) 계정은 두 경로로 열렸다.
  - 기기 ID만 보내도 API가 통과했다(`tokenOk`가 `true`).
  - 처음 `/session`을 연 사람이 토큰을 받았다. 기기 ID를 알아낸 사람이 먼저 열면 계정을 가져갈 수 있었다.
- **후**
  - 토큰이 없는 계정은 API도 세션 열기도 거절한다(`legacy_locked`). 앱은 새 기기 ID로 새로 시작하고, MY에 “이전 기록이 잠겨 있어요”를 보여 준다.
  - 이전 기록이 필요하면 운영자가 사용자를 확인한 뒤 어드민에서 **일회용 이어받기 코드**를 만든다.
    - 8자, 30분 동안만 쓸 수 있고 한 번만 쓴다. 서버에는 해시만 저장한다.
    - 화면에 한 번만 보여 주고 주소(쿼리)에는 남기지 않는다.
  - 사용자가 앱 MY → “이전 기록 이어받기”에 코드를 넣으면 이 기기의 기기 ID·토큰이 이전 계정으로 옮겨 간다. 비어 있던 새 계정은 지운다.
    - 지금 기기에 새 기록이 있으면 섞지 않고 거절한다.
    - 시도는 사용자당 10분에 5번까지다.
    - 예전 기기의 푸시 토큰은 버린다.
  - 코드 발급과 이어받기는 검수 기록(`subject=account`)에 남긴다. 평가 데이터 내보내기에는 넣지 않는다.

### 1-5 AI 첫 후보가 틀려도 다른 식별 후보를 검증 — `server/src/findsearch.ts`
- **전**: 판매처 탐색은 식별 후보 중 **첫 번째 하나**만 찾았다.
- **후**
  - 확정된 식별이 있으면 그것 하나만 찾는다. 사용자의 “이 옷이 맞아요”나 운영자의 MATCH 공개가 확정이다.
  - 확정 전(AI 제안·운영자 LIKELY)이면 앞에서부터 **최대 3개 후보를 함께** 찾는다(`targetsToSearch`, `WALF_SEARCH_MAX_TARGETS`).
- **비용 한도**
  - 두 번째 후보부터는 검색어를 3개까지만 쓴다.
  - 상품 페이지 상세 확인은 모든 후보를 합쳐 6개까지다.
  - 막힌 소스는 다음 후보에서 다시 두드리지 않는다.
  - 무료 소스만 쓰고, AI는 부르지 않는다.
- 매물마다 모든 후보로 검증한 뒤 가장 가까운 후보 기준 결과를 쓴다(`verifyBest`). 어느 후보 기준인지 `offers.target_ref`·`target_rank`에 남는다.
  - 어드민은 “식별 후보 2 기준” 태그와 후보별 품번 일치 수를 보여 준다.
  - 탐색 요약은 “식별 후보 2개 탐색(후보 1·후보 2)”처럼 나온다.

## 4. 바뀐 동작(운영·사용자가 체감하는 것)
- 할인가만 목표 이하인 매물은 새 매물 알림이 가지 않는다(“확인하지 못한 조건”으로 운영자·사용자 화면에 보임).
- 상품명만 같은 상품 페이지로 기다려줘를 걸면 운영자가 “같은 상품 페이지 맞음”을 눌러야 알림이 간다.
- 이전 버전 앱 계정은 기기 ID만으로 열리지 않는다(새로 시작 → 필요하면 이어받기 코드).
- 확정 전 식별이면 판매처 탐색이 후보 최대 3개를 찾는다. 검색어는 최대 6+3+3개다. 상세 확인 6개 한도는 그대로다.

## 5. 남은 기술적 위험
- **브랜드 별칭 의존**: 한글·영문 표기 차이는 별칭으로만 같은 브랜드가 된다. 별칭이 없으면 같은 상품을 “다른 상품”으로 볼 수 있다. 알림이 잘못 나가는 쪽이 아니라 놓치는 쪽이다. 별칭 보강이 필요하다.
- **품번 표기 다양성**: 공백으로 나뉜 품번(“W JKT26 055”)이나 다른 구분 기호는 일치로 보지 않는다. 역시 놓치는 쪽이다.
- **사진 비교 없음**: 같은 옷인지는 품번·브랜드·상품명으로만 본다. 사진 비교는 연결 전이다.
- **할인가 규칙**: 공식몰이 모든 사람에게 적용하는 할인가도 “적용 조건 미확인”으로 본다. 알림이 보수적이다.
- **다중 후보 비용**: 무료 소스뿐이지만, 확정 전 의뢰는 검색 요청이 최대 2배 정도 늘어난다(같은 판매처 요청 간격 유지).
- **이어받기**: 운영자의 본인 확인 절차에 의존한다. 코드는 8자(약 40비트)·30분·1회·시도 제한이다. 이어받기 화면은 MY 안 “테스트 빌드 설정” 근처에 있는 베타용 화면이다.
- **토큰 저장**: 앱 토큰은 여전히 AsyncStorage에 있다(키체인 아님, Gate D와 같음). `WALF_SECRET`을 고정하지 않으면 재시작마다 사진 주소·로그인이 만료된다.
- **실제 판매처 1곳**: 자동 탐색의 실제 판매처는 BADBLOOD 공식몰뿐이다. 다른 브랜드는 “찾아볼 수 있는 실제 판매처가 없어요”로 보인다.
- **시뮬레이터 QA 범위**: 새 의뢰 접수는 앱 사진 올리기 대신 QA 스크립트로 넣었다(접수 화면은 이번에 바꾸지 않음). 실기기·푸시는 확인하지 않았다.
