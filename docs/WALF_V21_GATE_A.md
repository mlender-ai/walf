# WALF V2.1 · Gate A 보고 — 찾아줘 판매처 탐색 파이프라인과 실제 상품 데이터 구조

- 작성: 2026-11-16 · 브랜치 `feat/walf-v2.1`(기준: `feat/walf-v2` 67fb638, PR #1 병합 전)
- 범위: 지시서 STEP 1(탐색 파이프라인)과 STEP 2의 데이터 구조. 결과 화면(STEP 3)·대체 추천 흐름은 Gate B에서 해요.
- 앱 화면은 바꾸지 않았어요. 사용자에게는 검수 전 탐색 결과가 보이지 않아요(기존 정책 그대로).

## 1. 무엇이 바뀌었나

AI 식별(“어떤 옷인가”)과 판매처 탐색(“그 옷을 어디서 파는가”)을 나눴어요.

- **식별 결과:** `product_identities` · `ai_identities`. 기존과 같아요.
- **판매처 탐색 결과:** 새 표 `offer_searches` · `offers`에 따로 저장해요.

AI가 옷을 식별했다는 사실만으로는 “판매 중인 매물이 있다”고 판단하지 않아요.

### 탐색 7단계 — 단계마다 독립 함수와 테스트

| 단계 | 함수(`server/src/findsearch.ts`) | 하는 일 | 테스트 |
|---|---|---|---|
| 1 식별 | `targetsOf` | 식별 결과를 탐색 대상으로 바꿔요. 근거가 강한 순서는 사용자 확인 > 운영자 공개 > AI 제안이고, 숨김 후보는 빼요 | `[1 식별]` |
| 2 검색 조건 | `buildQueries` | 품번 → 브랜드+품번 → 브랜드+모델명 → 모델명 → 한글 브랜드+모델명 순이에요. 중복 검색어는 빼요 | `[2 검색 조건]` |
| 3 소스 검색 | `searchSources` + `SearchSource`(`searchsources.ts`) | 소스마다 따로 돌아서 한 곳이 실패해도 나머지는 계속해요. 막힌 곳은 다시 열지 않아요. 쓸 수 없는 소스는 “검색하지 않음”과 그 이유를 남겨요 | `[3 소스 검색]` 4개 |
| 4 통합 | `mergeHits` | 같은 페이지는 하나로 합쳐요(추적 쿼리·www 무시, 검색어는 모아 둠). 같은 품번은 같은 상품 묶음으로 묶어요 | `[4 통합]` |
| 5 정리 | `normalizeHits` | 같은 상품일 가능성이 큰 페이지부터 상세를 최대 6개 읽어요(이미지·판매가·할인가·배송비·옵션별 재고). 못 읽은 페이지는 그렇게 표시해요 | `[5 정리]` |
| 6 검증 | `verifyOffer` · `compareProduct`(`sameproduct.ts`) | 품번·브랜드·상품명으로 같은 상품인지 판정하고, 원하는 색·사이즈·상태·희망가는 따로 적어요. 사진 비교는 하지 않았다고 표시해요 | `[6 검증]` |
| 7 결과 | `assemble` · `rankOffers` | 식별 결과와 판매 매물 결과를 나눠 돌려줘요. 매물은 같은 상품·가능성 높음·확인 못 함·다른 상품으로 묶고, 소스별 처리와 한계를 함께 담아요 | `[7 결과]` |

`runFindSearch`가 1→7을 잇고, `createOfferSearcher`가 대기열을 돌려요.

- **AI를 부르지 않아요.** 무료 소스만 써요.
- **자동 대기열:** 찾아줘가 진행 중(접수·7일 탐색)이면 식별·공개·사용자 확인으로 대상이 생기거나 바뀔 때 자동으로 넣어요(`ensureFindSearches`).
- **같은 조건 다시 검색 막기:** 대상과 소스가 같으면 20시간 안에는 다시 검색하지 않아요. 다른 의뢰가 같은 옷을 찾으면 소스를 다시 열지 않고 결과만 그 의뢰 조건으로 다시 검증해 써요. 운영자가 “다시 실행”을 누르면 새로 검색해요.
- **실패한 탐색:** 하루 동안 자동으로 다시 넣지 않아요.
- **서버 재시작:** 끊긴 탐색은 다시 대기열에 넣어요. 같은 탐색이 세 번 끊기면 멈춰요.

### 판정 규칙 — 기다려줘와 공통(`sameproduct.ts`)

| 자동 판정 | 조건 | 뜻 |
|---|---|---|
| `same_code` 같은 상품 | 찾는 옷의 품번이 페이지 상품명에 있음 | 품번 기준으로 같은 상품. 그래도 운영자 확인 전에는 “구매 가능”으로 확정하지 않아요 |
| `likely` 가능성 높음 | 브랜드가 맞고 상품명 핵심 단어가 80% 이상 같음 | 품번이 없는 페이지 |
| `unverified` 확인 못 함 | 표기·언어가 달라 판단할 수 없음, 또는 상세를 못 읽음 | 운영자가 확인해야 해요 |
| `different` 다른 상품 | 품번이나 브랜드가 다름 | 같은 모델의 다른 색이 품번이 다르면 여기에 들어가요(예: W-JKT26-054 블루그레이) |

기다려줘의 페이지 동일성 판정도 같은 함수로 옮겼어요. 동작은 기존과 같고, 기존 테스트 84개가 모두 통과해요.

## 2. 실제 상품 후보 데이터 구조(STEP 2)

하나의 모양(`ProductOffer`, `server/src/offers.ts`)을 두 곳이 같이 써요.

- 판매처 탐색: `relation=same`
- 대체 상품 추천: `relation=similar`

`SimilarProductProvider`(패션 브레인 연결 자리)도 이 모양으로 결과를 돌려주게 바꿨어요. 외부 엔진이 준 값은 반드시 `cleanOffer`를 거쳐요.

`cleanOffer`가 버리거나 무시하는 값은 다음과 같아요.

- 주소·판매처·이름·추천 모델·버전 중 하나라도 없으면 그 후보를 버려요.
- 외부 엔진이 “같은 상품”이라고 판정해도 믿지 않고 `unverified`로 둬요.
- `mock://` 주소는 테스트 소스가 켜졌을 때만 받아요.

| 지시서 요구 | 필드(`offers` 표) |
|---|---|
| 브랜드 · 제품명 | `brand` · `name`(+ 제목에서 읽은 `model_code`) |
| 상품 이미지 | `image_url` — 판매처 이미지 주소만 저장하고, 서버로 내려받지 않아요 |
| 판매처 | `seller` · `source` |
| 가격 및 통화 | `price` · `sale_price` · `shipping` · `currency`(기본 KRW). 총액은 배송비를 알 때만 계산해요 |
| 사이즈·색상 | `options`(색·사이즈·재고·가격) · `want_size`(ok·sold_out·missing·unknown) · `want_color`(ok·other·unknown) · `stock` |
| 상품 페이지 URL | `url` · `url_key`(+ `listing_id` — 같은 페이지는 `listings`에 한 줄, 처음 본 시각으로 새 매물을 가를 수 있어요) |
| 유사한 디자인 요소 | `similar_points` — 지금은 일치한 근거. 대체 추천에서는 디자인 요소가 들어가요 |
| 원래 제품과 다른 요소 | `diff_points` |
| 검증 상태 | `verdict`(자동 판정) · `checks`(품번·브랜드·상품명·색·사이즈·사진 항목별 일치·불일치·확인 못 함·미실시) · `detail`(fetched·listed_only·failed) · `review_state`(운영자 검수: pending·confirmed_same·rejected) |
| 추천 모델 및 버전 | `recommender` · `recommender_version` · `score`. 이번 탐색은 `walf-rules` / `find-search-1` |

DB는 스키마 v2 → v3로 올렸어요. 새 표만 더했고, 파일 DB는 올리기 전에 `VACUUM INTO` 사본을 남겨요(기존 방식 그대로). 계정을 삭제하면 그 사용자 의뢰의 탐색·후보도 함께 지워져요. 판매처 상품 페이지 기록(`listings`)은 개인 정보가 아니라서 남아요.

## 6. 검색 후보 데이터 — 실제(2026-11-16, 1회)

BADBLOOD 공식몰에서 실제로 1회 탐색했어요. 사이트 부담을 줄이려고 같은 날 요청은 10건 안팎으로 끝냈어요(robots.txt 포함).

| 항목 | 결과 |
|---|---|
| 걸린 시간 | 약 3초(검색 2회 + 상품 페이지 1개) |
| 검색어 | `W-JKT26-055` → 상품 페이지 1개 · `Mystic Nylon Track Jacket` → 같은 페이지 |
| 후보 | `[w-jkt26-055] 미스틱 나일론 트랙 자켓 - 네이비` · **같은 상품(품번 일치)** · 판매가 189,000원 → 할인 170,100원 · 배송비 페이지에 없음 · 이미지 읽음 |
| 사이즈 재고 | 네이비 S·M·L **모두 품절**(옵션 재고 데이터 기준). 원하는 M = 품절 |
| 검색하지 않은 곳 | 11곳(테스트 소스, 네이버·AI 웹은 대기, 약관·확인 전 판매처) |

이 과정에서 공식몰 페이지의 첫 `og:image`가 상품 사진이 아니라 쇼핑몰 배너라는 것을 발견했어요. 그래서 상품 이미지는 구조화 데이터의 옵션 이미지를 먼저 쓰도록 고쳤어요(`sources.ts`). 기다려줘의 상품 이미지도 같은 해석을 써요.

## 7. 한계 · 확인하지 못한 것

1. **실제로 쓸 수 있는 소스가 공식몰 1곳뿐이에요.** 다른 브랜드는 공식몰을 등록하기 전까지 실제 탐색 결과가 없어요. 등록된 공식몰도 새 상품 정가 판매처라서, 중고·리셀 매물은 지금 구조로 찾을 수 없어요(약관·제휴 대기).
2. **사진으로 같은 옷인지 비교하지 않아요.** 품번·브랜드·상품명만 봐요. 품번이 없는 판매처(중고 매물 등)는 대부분 “가능성 높음”이나 “확인 못 함”이에요.
3. **공식몰 검색에 한글 모델명을 쓰지 못해요.** AI 식별이 영문 모델명만 주면 공식몰 자체 검색은 품번에 기대요. 품번이 없는 상품은 공식몰에서 못 찾을 수 있어요.
4. **배송비가 상품 페이지에 없는 쇼핑몰이 많아요.** 이 경우 총액을 만들지 않고 “배송비 모름”으로 둬요.
5. **판매처 이미지·가격을 사용자에게 보여 줄 권리는 확인 전이에요.** 공식몰 약관 제22조 ②(얻은 정보의 영리 목적 복제·배포 금지)는 법무 확인이 필요해요. 지금은 이미지 주소만 저장하고, 어드민에서만 보여요.
6. **네이버 쇼핑 API는 실제 응답으로 검증하지 않았어요.** 공식 응답 형식에 맞춘 가짜 응답으로만 테스트했어요.
7. **운영자 검수 버튼(같은 상품 확인·제외)은 아직 없어요.** `review_state` 필드만 있고, 화면은 Gate B·D에서 만들어요.

## 8. 다음 — Gate B 제안

1. 찾아줘 결과 화면(앱)에서 정확한 동일 상품·가능성 후보·대체 상품·탐색 실패를 구분해 보여 줘요. 운영자가 검수한 후보만 보여 주고, 검수 전 잠정 결과를 보여 줄지는 화면 시안과 함께 제안해요.
2. 어드민에 후보 검수를 넣어요(같은 상품 확인·제외·사유). 기존 7일 탐색의 후보 등록과 연결해요.
3. `SimilarProductProvider`에 권리가 확인된 테스트 Fixture를 연결하고, 실제 상품 카드(사진·가격·비슷한 점·다른 점)로 대체 상품을 보여 줘요. 브랜드만 나열하는 기존 DISCOVER와 구분해요.
